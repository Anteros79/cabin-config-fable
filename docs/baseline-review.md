# Baseline review — Cabin Kit (original implementation)

Capability assessment of the baseline application so a replacement can be compared against it.

- Evidence paths are relative to `inspection/baseline-copy/` (a byte-identical copy of the original `app/`, `tests/`,
  `README.md`, `pyproject.toml`, `uv.lock`). `file:line` refers to that copy.
- **run** = observed in the inspection run of 2026-11-14 (commands, versions and outputs in
  `inspection/baseline-run-record.md`, raw logs in `inspection/logs/`). **read** = taken from the source, not executed.
- Automated result of that run: `pytest` 52 passed / 0 failed in the locked environment; `ruff check` 0 findings.
- **No browser was run.** Everything about the 3D scene, the 2D map, dialogs, printing and mobile layout is *read*.
  `tests/browser_smoke.py` exists but was not executed.

The baseline is about 560 lines of application Python, 190 lines of hand-minified JavaScript (lines up to 846
characters) and vendored Three.js r180. All data is fictional and generated in code.

## 4. Vendored renderer and licence

`app/static/vendor/` holds `three.core.js` (1.40 MB), `three.module.js` (0.60 MB), `OrbitControls.js`,
`RoundedBoxGeometry.js` and `THREE-LICENSE.txt` (MIT, "Copyright © 2010-2025 three.js authors"), loaded through an
import map (`app/static/index.html:5`) with no CDN and no build step. In this run all five files were found
byte-identical to the public npm package `three@0.180.0` (`inspection/logs/vendor-verify.txt`); `REVISION` is `'180'`.
Gaps: the baseline ships no version or checksum manifest of its own (the README's "verified with SHA-512" cannot be
re-checked from the repository), the two add-on files carry no licence header and rely on the separate licence file,
and the 2 MB of unminified modules are served uncompressed with `Cache-Control: no-store`.

## 5. Behaviours worth preserving

1. **Never guess.** Explicit refusal states; ambiguous or missing applicability yields no part and a visible gap.
2. Inclusive date boundaries on both ends, applied to configuration, rule, substitute and source document alike.
3. Specificity by strict superset, with a variant selector implying the variant's attributes.
4. The visit stores the resolved configuration and rules at start; validation and reports use that snapshot, so later reference changes cannot alter a visit.
5. One record per visit/location/component with upsert; a substitute replaces the primary; mandatory panels are added and totalled by the server, never by the client.
6. Parts, units and sources are always derived server-side from the snapshot; the request carries only ids.
7. Write transactions that re-check status under `BEGIN IMMEDIATE`; completion refused when empty, idempotent when repeated, 409 on any edit afterwards.
8. Separate reference and visit stores, read-only reference connection, atomic rebuild through a temp file and rename.
9. Deterministic fictional dataset with named demo cases (the tails, dates and part numbers in §2–§3) and prominent "fictional / not for maintenance use" labelling in UI and report.
10. Self-contained front end: vendored, licence-carrying renderer; no CDN; DOM built with `textContent` only.
11. Scene driven by the snapshot's seat list; instanced seats; render on demand; layer toggles that also restrict picking; click-vs-drag threshold; 2D fallback and a location menu.
12. Tests that build both stores in `tmp_path` and never touch default paths.
